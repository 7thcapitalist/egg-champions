# Game factory

Takes a game spec and produces a published Roblox game. Each agent has one
job, reads files from this repo, and writes files back.

Nothing in `factory/` names a game. One game lives in one folder under
`games/`, so a second game is a new folder and a new spec. Below, `<game-dir>`
means that folder. Every tool takes the game folder or explicit paths as
arguments.

| # | Agent | Reads | Produces | Status |
| --- | --- | --- | --- | --- |
| 1 | Spec parser | `<game-dir>/spec.md` | `<game-dir>/config/*.json` | Working |
| 2 | Economy tuner | `<game-dir>/config/` | `<game-dir>/tuning/` gym stats, pacing report, proposals | Working |
| 3 | Planner | Spec and config | Task list for the coder | Working |
| 4 | Coder | One task at a time | Game code and tests | Working, run by the orchestrator |
| 5 | Asset maker | Pet roster, style guide | 3D models | Not built |
| 6 | World builder | World table | Worlds generated by code | Not built |
| 7 | Playtester | Published test place | Bug report | Not built |
| 8 | Publisher | A passing build | Live game, icon, thumbnails | Not built |

The local orchestrator starts fresh `codex exec` runs. It loads each role's
instruction body from the historical `.claude/agents/` files:

| Agent | File |
| --- | --- |
| 1 Spec parser | [`.claude/agents/spec-parser.md`](../.claude/agents/spec-parser.md) |
| 2 Economy tuner | [`.claude/agents/economy-tuner.md`](../.claude/agents/economy-tuner.md) |
| 3 Planner | [`.claude/agents/planner.md`](../.claude/agents/planner.md) |
| 4 Coder | [`.claude/agents/coder.md`](../.claude/agents/coder.md) |

Their scripts live in `factory/tools/`, standard library only.

Briefs in `factory/tasks/` change the factory itself. Briefs in
`<game-dir>/tasks/` build one game.

## State and gates

Agents coordinate through files, not through a person.
`<game-dir>/state.json` is the single record of progress for one game: a
`game` name and a list of `stages`, each with `id`, `status` (pending,
running, passed, failed, blocked), `attempts`, `note` and `updated`. The
stages run in order: `spec_parsed`, `economy_tuned`, `planned`, `built`,
`assets`, `worlds`, `playtested`, `published_test`.

    python factory/tools/state.py show <game-dir>
    python factory/tools/state.py set <game-dir> <stage> <status> [--note TEXT]
    python factory/tools/state.py next <game-dir>

A gate is the machine check for one stage. It only reads what is already in
the repo, so a stale generated file fails the gate instead of being quietly
regenerated. Stages with no check yet print "no gate yet" and exit 1, so
"not implemented" can never be mistaken for "passed".

    python factory/tools/gate.py <game-dir> <stage>

| Stage | Gate today |
| --- | --- |
| `spec_parsed` | the validator passes and `manifest.json` matches the spec's current hash |
| `economy_tuned` | the tuning report shows the time pacing targets met |
| `built` | every brief in the game's task index is ticked, and the Luau suite, rojo, selene and stylua pass |
| `assets` | every pet and egg has a current entry in `assets/models.json`, the project maps it, `rojo build` passes, and `assets/verify.json` checked this exact `models.json` with every entry ok |
| the rest | no gate yet |

`gate.py` decides; `state.py` only records what it found. Nothing marks a
stage passed on its own word.

## Assets

Three files in `<game-dir>/assets/`:
- `manifest.json`: the approved mesh and texture ids per pet and egg, by hand
  or by the asset maker.
- `models.json`: the model table the game loads, mapped to
  `ReplicatedStorage.GameConfig.models`. Rebuild it after any manifest change:

      python factory/tools/build_models.py <game-dir>

- `verify.json`: what Roblox itself made of every entry. The server's
  `ModelLibrary` builds each template with `CreateMeshPartAsync` at start;
  this checks the same call in an Open Cloud Luau Execution task on the test
  place. It needs the API key in the environment variable that `roblox.json`
  names (load `.env` first) with the scope
  `universe.place.luau-execution-session:write`:

      set -a; . ./.env; set +a
      python factory/tools/verify_assets.py <game-dir> [--wait SECONDS]

  Exit 2 means the task is still running; run it again to resume it.

## CI

The Roblox steps run in GitHub Actions on the owner's repo
(`.github/workflows/roblox.yml`), with the API key in the repo secret
`ROBLOX_API_KEY`. The key reaches each step only as an environment variable
and is never echoed. It runs on `workflow_dispatch` and on a push to `main`
that touches `games/**` or `factory/**`; a commit whose message contains
`[skip ci]` does not start it. One run at a time.

Steps, all on `games/egg-champions` and its TEST place only:
1. Install rojo 7.7.1 (`rojo-7.7.1-linux-x86_64.zip` from the rojo release).
2. `build_models.py` rebuilds `assets/models.json`.
3. `texture_jobs.py` saves each texture in `assets/texture_jobs.json` whose
   manifest entry still has `needs_texture_save`: a Luau Execution task reads
   the snippet from the place, runs it, and uploads the EditableImage with
   `AssetService:CreateAssetAsync`. The new id goes into the manifest.
4. `verify_assets.py --if-stale` checks every model on Roblox, unless
   `verify.json` already covers this exact `models.json` with every entry ok.
5. `gate.py <game-dir> assets`. If it passes, the `assets` stage is recorded
   (only when not already passed) and `publish_test.py` publishes the rojo
   build to the test place. It refuses while a texture job is pending,
   because publishing replaces the place content the job reads.
6. Any change to `manifest.json`, `models.json`, `verify.json` or
   `state.json` is committed back to `main` by `github-actions[bot]` with a
   message ending in `[skip ci]`. The run fails if a texture job, the check
   or the gate failed.

Reruns are safe: a saved texture is never uploaded again, a current
`verify.json` is not rechecked, and nothing is committed when nothing changed.
Each successful gate does publish a new test place version.

The API key (Creator Dashboard, Open Cloud API keys) needs, for the TEST
universe only:

| Step | Scope | Source |
| --- | --- | --- |
| Luau Execution tasks (verify, texture jobs) | `universe.place.luau-execution-session:write` | create.roblox.com/docs/cloud/reference/features/luau-execution |
| Asset upload from a task (`CreateAssetAsync`) | `asset:write` (the `assets` API system, Write) | create.roblox.com/docs/cloud/guides/usage-assets |
| Place publishing | `universe-places:write` | create.roblox.com/docs/cloud/reference/features/places |

The AssetService reference says `CreateAssetAsync` works in the Luau
Execution context when `CreatorId` and `CreatorType` are given, but names no
key scope; `asset:write` is the scope Open Cloud uses for creating assets.
If the key has accepted IP addresses set, Actions runners need `0.0.0.0/0`,
since their addresses change from run to run.

## Build a game

    rojo build <game-dir> -o <game-dir>/build/game.rbxl
    selene <game-dir>/src
    stylua --check <game-dir>/src

## Run the factory

One command builds a game from where its `state.json` says it is, with nobody
typing. Use a clean, isolated checkout; the orchestrator refuses a dirty
working tree, including unrelated untracked files:

    python factory/tools/run_factory.py <game-dir>

See [`RUN-CODEX.md`](../RUN-CODEX.md) for the daily Codex procedure and the
current game's validation commands.

What it does, in order:
- Works on the first stage that has not passed. A stage whose gate already
  passes is recorded and skipped. `spec_parsed`, `economy_tuned` and
  `planned` run their agent, then the gate, up to 3 tries.
- `built` walks `<game-dir>/tasks/index.json` in dependency order. Each task
  gets a fresh headless `codex exec` run on its one brief. The
  coder does not commit. The orchestrator then checks the work itself:
  - only allowed paths changed: `<game-dir>/src/`, `<game-dir>/tasks/`, test
    files (`*.spec.luau`, `factory/tools/run_tests*`), and files the brief
    names. A change to the spec, `config/`, `tuning/`, `state.json`, the task
    index, `factory/`, `.claude/` or `.env` rejects the attempt and reverts
    all of it;
  - every Done-when box is ticked, and no changed file has an em dash;
  - the brief's Done-when commands pass (`python`, `rojo`, `selene`,
    `stylua`, and `grep ... finds no` checks are rerun; experiment items such
    as "a deliberately broken ..." rely on the coder's tick);
  - the test entry point, `rojo build`, `selene` and `stylua --check` pass.
- Pass: the task is marked done and committed locally. Fail: the coder gets
  the failing output and tries again, up to 3 tries in all. Still failing:
  the work is saved to `<game-dir>/reports/blocked/task-<id>.patch`,
  reverted, the task is marked blocked, and the run stops.
- A stage with no agent yet (today `assets` onward) stops the run.

Limits: `--max-tasks` (default 5) tasks per run, `--task-minutes` (default 60)
per task across its attempts, and `--attempts` (default 3). `--budget-usd` is
rejected because Codex CLI has no equivalent measured spend cap here. Codex
runs with `workspace-write` and `approval_policy=never`; the orchestrator's
path guard and Git preflight enforce the task boundary. It removes
`ROBLOX_API_KEY` from the agent environment. Nothing in the loop publishes.
Commits stay local unless `--push` is explicitly supplied. Do not use
`--push` on `main`: the CI workflow publishes the TEST place on relevant pushes.

Every step adds a line to `<game-dir>/reports/run-log.md`. Every run ends by
rewriting `<game-dir>/reports/latest.md`: what was done, what failed, the
state now, and what to do next. Each agent's final report and JSONL trace are
kept in `<game-dir>/reports/agents/`.

### Resume after a blocked task

1. Read `<game-dir>/reports/latest.md`, then the coder reports and the saved
   patch it names.
2. Fix the cause. Usually that is the brief (a wrong premise, or a check no
   machine can run), sometimes the code or a tool. To keep the coder's last
   try, `git apply <game-dir>/reports/blocked/task-<id>.patch` and finish it.
   Commit the fix.
3. Run again with the task set back to pending:

       python factory/tools/run_factory.py <game-dir> --unblock <id>

A blocked stage other than `built` resumes the same way, after
`python factory/tools/state.py set <game-dir> <stage> pending`.

`--agent-cmd CMD` swaps `codex exec` for another command, which gets the prompt
on stdin. It exists only to test the orchestrator itself without spending
agent runs.

`--finish ID` is for agents whose shell calls are cut short (for example a
45 second limit). The agent builds task ID in the working tree and ticks its
Done-when boxes, then runs
`python factory/tools/run_factory.py <game-dir> --no-push --finish ID`.
It applies the same path guard and checks as a normal attempt (the checks
run side by side), then marks the task done and commits it. It skips the
stage gates and the run report, and it never reverts: on failure it prints
what failed and the agent fixes it and runs it again. Only the next runnable
task can be finished.
